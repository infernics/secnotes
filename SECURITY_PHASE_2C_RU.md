# SecNote 1.4.14 — отчёт по этапу 2C

## Этап

**Безопасная миграция потоков файлового хранилища из SNF1 в SNF2.** Базой служит архив этапа 2B; изменения этапов 1, 1.1, 2A и 2B сохранены.

## Что сделано

1. Добавлена автоматическая миграция старого файла `SNF1` в контекстно-привязанный `SNF2` при загрузке списка файлов. Миграция также запускается перед экспортом и созданием миниатюры, чтобы отдельное обращение к файлу не обходило обновление.
2. Перешифрование потоковое: данные не загружаются целиком в оперативную память. На время преобразования расшифрованное содержимое помещается во временный файл в приватном cache-каталоге приложения.
3. Перед заменой исходный зашифрованный файл сохраняется под отдельным резервным именем. Новый файл проверяется расшифрованием, контекстом ID, размером и SHA-256 исходного содержимого.
4. Только после проверки и синхронизации нового файла старый резервный экземпляр удаляется. Ошибка до подтверждения нового файла приводит к попытке восстановления исходного файла.
5. Добавлено восстановление после прерывания процесса:
   - если исходный файл уже перемещён, но новый ещё не установлен, резервная копия возвращается на исходное место;
   - если новый `SNF2` уже установлен, он повторно проверяется, после чего оставшаяся резервная копия удаляется;
   - если новый файл не проходит проверку, выполняется откат к резервной копии.
6. Ошибка миграции не блокирует чтение старого `SNF1`: исходный файл остаётся на месте, а попытка миграции повторится при следующем обращении.
7. В список очистки временных plaintext-файлов добавлены остатки миграции.
8. Добавлен тест преобразования `SNF1` → `SNF2`, проверки содержимого и отказа при другом ID.

## Совместимость и ограничения

- Старые `SNF1` продолжают расшифровываться; принудительного удаления или массового сброса файлов нет.
- Новые и мигрированные файлы используют `SNF2` и AAD с доменом `file-data` и ID объекта.
- Резервный архивный поток `SNF1` не менялся: формат внешних резервных копий остаётся совместимым.
- Миграция выполняется по мере открытия списка/обращения к файлам, а не отдельной массовой операцией при запуске. Для больших старых файлов требуется дополнительное свободное место под временный plaintext и новую зашифрованную копию. Если места не хватает, исходный зашифрованный файл сохраняется.
- Перезапись временных файлов и старых копий является best-effort. Физическое удаление блоков на flash-накопителях гарантировать нельзя.

## Проверки, выполненные в рабочей среде

- `Crypto.kt` скомпилирован отдельно через `kotlinc`.
- Smoke-тест реального преобразования `SNF1` → `SNF2` завершился успешно: `SNF1 -> SNF2 migration smoke test: OK`.
- Файл тестов `CryptoTest.kt` скомпилирован отдельно с тестовыми заглушками JUnit и friend-path для `internal` API.
- Проверен баланс скобок в изменённом `FileVaultRepository.kt`.
- Полная Android-сборка, Android/JUnit suite и проверка поведения на реальном устройстве в этой среде не выполнялись: Gradle wrapper в проекте отсутствует, Android SDK/Gradle не установлены. Требуется подтверждение GitHub Actions.

## Не менялось

- Минимальная длина пароля не вводилась; ограничения на максимальную длину не добавлялись.
- Принудительная блокировка приложения не вводилась; существующие настройки автоблокировки сохранены.
- KDF, настройки биометрии, release-подпись и формат внешних резервных копий в этом этапе не менялись.

## Результат

Этап 2C подготовлен для CI-проверки. До зелёного результата GitHub Actions и проверки работы на устройстве release-сборку не создавать.

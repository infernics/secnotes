SECNOTE 1.4.1 — ИСПРАВЛЕНИЕ СБОРКИ И ИНСТРУКЦИЯ GITHUB

ЭТО ОБНОВЛЕНИЕ ДЛЯ СУЩЕСТВУЮЩЕЙ РАБОЧЕЙ SECNOTE 1.3.3.
Новый репозиторий создавать не нужно. Старое приложение с телефона не удалять.

ВАЖНО ДО НАЧАЛА
- Репозиторий GitHub должен быть Private.
- Package ID остаётся infernics.notes.
- Подпись APK должна совпадать с прежней.
- Не удаляйте и не заменяйте старый signing/secure-notes-debug.keystore.
- Не очищайте данные SecNote 1.3.3 перед установкой обновления.

1. СКАЧАТЬ И РАСПАКОВАТЬ
Скачайте SecNote-v1.4.1-Repo-Root.zip и распакуйте его на компьютере.
В корне распакованной папки должны быть видны:
  .github/
  app/
  signing/
  settings.gradle.kts
  build.gradle.kts
  gradle.properties
  README_RU.md
  GITHUB_UPDATE_GUIDE_RU.txt

2. ОБНОВИТЬ ФАЙЛЫ В СУЩЕСТВУЮЩЕМ РЕПОЗИТОРИИ
1) Откройте ваш текущий Private Repository с SecNote 1.3.3.
2) Перейдите на вкладку Code.
3) Нажмите Add file → Upload files.
4) Перетащите СОДЕРЖИМОЕ распакованной папки в корень репозитория. Не загружайте сам ZIP и не создавайте вложенную папку проекта.
5) Подтвердите замену файлов.
6) Если GitHub предлагает заменить keystore, пропустите signing/secure-notes-debug.keystore. Оставьте старый файл в репозитории.
7) Нажмите Commit changes и сохраните в ветку main.

ВАЖНО: скрытая папка .github может не отображаться в файловом менеджере.
Если workflow не обновился автоматически, откройте файл в GitHub:
  .github/workflows/build-apk.yml
Нажмите карандаш (Edit), замените весь текст содержимым файла
SecNote-v1.4.1-build-apk.yml и нажмите Commit changes.
Если файла ещё нет: Add file → Create new file, имя:
  .github/workflows/build-apk.yml
и вставьте туда содержимое скачанного YAML.

3. ПРОВЕРИТЬ КОНФИГУРАЦИЮ
В app/build.gradle.kts должны быть:
  applicationId = "infernics.notes"
  namespace = "infernics.notes"
  versionCode = 9
  versionName = "1.4.1"

В корне репозитория должен остаться прежний файл:
  signing/secure-notes-debug.keystore

Путь workflow должен быть строго:
  .github/workflows/build-apk.yml

4. ЗАПУСТИТЬ ОБЛАЧНУЮ СБОРКУ
1) Откройте вкладку Actions.
2) Выберите Build SecNote APK.
3) После commit сборка запускается автоматически. Если не запустилась, нажмите Run workflow и выберите main.
4) В логе проверьте шаг Verify project files and application identity.
5) Дождитесь зелёной галочки у Run unit tests and build APK.
6) Внизу успешного запуска откройте Artifacts и скачайте app-debug.apk.

Если будет красный крестик:
- Откройте шаг Run unit tests and build APK.
- Скопируйте первую строку Kotlin-компиляции с указанием файла и номера строки, а также сообщение Gradle What went wrong.
- Не меняйте файлы наугад.

5. УСТАНОВИТЬ ОБНОВЛЕНИЕ НА ТЕЛЕФОН
1) Не удаляйте SecNote 1.3.3.
2) Установите новый app-debug.apk поверх предыдущей версии.
3) Если Android пишет о конфликте подписи, остановитесь. Не удаляйте приложение с данными. Проверьте, что в GitHub остался исходный keystore.
4) После установки откройте настройки и проверьте версию 1.4.1.
5) При первом входе старая соль автоматически переносится под защиту Android Keystore; заметки и файлы не перешифровываются.

6. ПРОВЕРИТЬ НОВЫЕ ФУНКЦИИ
A. Главный экран и сортировка
- У обычных карточек больше нет отдельной подписи «Заметка».
- Удерживайте маркер перетаскивания справа и переместите запись выше/ниже.
- Перезапустите приложение и убедитесь, что порядок сохранился.

B. Автосохранение
- Откройте заметку и измените несколько символов.
- Подождите около секунды: статус должен сообщить об автоматическом сохранении.
- Вернитесь назад и откройте заметку снова.
- Повторите проверку для чек-листа: текст пункта и состояние галочки должны сохраниться.

C. Автоблокировка
В настройках последовательно проверьте:
- Мгновенно;
- 1 минута;
- 5 минут.
Сверните приложение и вернитесь до/после указанного времени. Если Android завершит процесс, повторный запуск всегда требует разблокировки.

D. Удаление и файловое хранилище
- Для проверки удаления используйте тестовую заметку и тестовый файл.
- Импортируйте тестовый файл. SecNote сначала создаёт зашифрованную копию и синхронизирует её на диск, затем запрашивает best-effort перезапись оригинала и его удаление.
- Если файловый провайдер не разрешил перезапись/удаление, приложение сообщит об этом. Оригинал нужно удалить вручную в исходном приложении.
- Проверьте массовое выделение, расшифровку и удаление тестовых файлов.

E. Секретный пароль уничтожения
- Текущий установленный секретный пароль сохраняется при обновлении.
- Сообщение «Попытки исчерпаны» теперь показывается 4 секунды.
- Не тестируйте самоуничтожение на основном хранилище с важными данными. Используйте отдельное тестовое устройство/хранилище и неважные тестовые записи.
- При введении секретного пароля приложение начинает очистку без подтверждения. При прерывании процедуры маркер заставляет SecNote продолжить очистку при следующем запуске.

7. ВАЖНЫЕ ОГРАНИЧЕНИЯ УДАЛЕНИЯ
Android-приложение не может гарантировать физическое стирание старых блоков NAND/flash, а также копий в облаке, резервных копиях и сторонних провайдерах. SecNote выполняет best-effort перезапись и удаляет собственные файлы, а для полного экстренного уничтожения дополнительно удаляет криптографические ключи.

НЕ ДЕЛАЙТЕ
- Не меняйте applicationId и namespace.
- Не меняйте versionCode на меньшее значение.
- Не удаляйте старое приложение до установки нового APK.
- Не удаляйте и не заменяйте keystore.
- Не делайте репозиторий публичным.
- Не публикуйте секретный пароль уничтожения.


ДОПОЛНЕНИЕ К ВЕРСИИ 1.4.1
В PanicCredential восстановлены внутренние функции createRecord/verifyRecord, которые использовались тестами версии 1.3.3. Это обеспечивает совместимость, если старый PanicCredentialTest.kt остался в репозитории после загрузки файлов поверх существующих. В архив 1.4.1 также включён актуальный тестовый файл. Удалять старые тесты вручную не требуется.


ПОЧЕМУ ПОЯВИЛАСЬ ОШИБКА В 1.4.0
В логе была ошибка compileDebugUnitTestKotlin: старый файл app/src/test/java/infernics/notes/PanicCredentialTest.kt вызывал PanicCredential.createRecord() и verifyRecord(), но эти методы отсутствовали в PanicCredential.kt версии 1.4.0. Это произошло потому, что при загрузке файлов поверх старого репозитория GitHub заменяет совпадающие пути, но не удаляет файлы, которых нет в новом ZIP.

ЧТО ИСПРАВЛЕНО В 1.4.1
- Возвращены internal-функции createRecord(password, salt) и verifyRecord(password, record) с совместимым контрактом версии 1.3.3.
- PanicCredential.set/verify используют эти же функции, чтобы тестируемая логика совпадала с рабочей.
- PanicCredentialTest.kt включён в архив и тестирует правильный/неверный пароль, повреждённую и усечённую запись.
- Workflow проверяет наличие теста и API до запуска Gradle.
- versionName = 1.4.1, versionCode = 9.

Поэтому старый PanicCredentialTest.kt в GitHub удалять вручную не требуется: API совместимости теперь восстановлен, и тест должен компилироваться. Всё равно загружайте содержимое всего архива в корень существующего репозитория, подтверждая замену файлов.

# SecNote 1.4.14 — отчёт об этапе 1 исправлений

Дата: 19 ноября 2026 г.
Исходник: `SecNote-v1.4.14-Repo-Root(1).zip`

## Область этапа

Этап 1 направлен на сохранность пользовательских данных при ошибках записи, аварийном завершении процесса, импорте файлов и восстановлении резервной копии.

Криптографический формат заметок и файлов, KDF, пароли, параметры автоблокировки, настройки пользователя и подпись промежуточной debug-сборки на этом этапе не менялись.

## Что изменено

### 1. Общий безопасный механизм записи

Добавлен `AtomicFileIO.kt` на базе `android.util.AtomicFile`:

- новая версия файла сначала записывается во временный файл механизма AtomicFile;
- вызов `fd.sync()` производится до фиксации;
- после фиксации файл перечитывается и сравнивается с ожидаемыми байтами;
- ошибка фиксации, включая ситуацию, когда Android не сообщил об ошибке `rename` исключением, больше не считается успешным сохранением;
- незавершённая первая запись `.new` удаляется, если базовый файл так и не появился;
- операции через помощник сериализованы, поскольку `AtomicFile` сам по себе не предоставляет блокировку потоков;
- поддерживается восстановление старого sidecar `.bak`.

Общий механизм подключён к записи заметок, key-файлов, метаданных скрытого хранилища, записи аварийного пароля и маркеров транзакций/очистки.

### 2. Заметки и автосохранение

- Убрана опасная схема fallback, которая при неудачном переименовании могла открыть прежний файл с усечением и затем копировать поверх него.
- Чтение заметок использует восстановление `AtomicFile`.
- При удалении учитываются базовый файл и служебные файлы AtomicFile.
- `NoteSaveQueue` теперь передаёт `Result<Unit>` вызывающему коду вместо подавления ошибки.
- Редактор показывает реальный статус сохранения; при ошибке не закрывается и не сообщает об успехе.
- Устаревший ответ сохранения не может пометить более новую редакцию текста как сохранённую.
- Ошибка удаления заметки также остаётся видимой пользователю.
- При ошибке сохранения перестановки список перечитывается с диска и показывается уведомление.

### 3. Импорт и файловое хранилище

- Во время шифрования исходный поток одновременно хешируется SHA-256.
- Созданная зашифрованная копия повторно расшифровывается в поток, направленный в digest sink без создания открытого временного файла.
- Сверяются SHA-256 и фактический размер исходных данных.
- Зашифрованные метаданные также перечитываются и проверяются.
- После фиксации пары файлов синхронизируется каталог, затем проверяются конечные пути данных и метаданных.
- Попытка перезаписать/удалить оригинал возможна только после успешной проверки конечной зашифрованной копии.
- Экспорт проверяет размер расшифрованного временного файла относительно зашифрованных метаданных.
- Уборка orphan-файлов учитывает `.meta.enc.bak`, чтобы не удалить данные, у которых метаданные ещё могут быть восстановлены AtomicFile.

### 4. Резервное копирование и откат

- Маркер восстановления записывается через проверяемую атомарную запись.
- Восстановление/откат проверяют допустимые и уникальные имена объектов в индексе отката.
- Все обязательные snapshot-файлы проверяются до начала удаления текущих данных.
- Содержимое snapshot и результат копирования сверяются SHA-256 по дереву файлов.
- Удаление текущих данных при восстановлении стало строгим: ошибка чтения каталога или удаления останавливает транзакцию.
- Перед заменой/откатом удаляются также `.bak` и `.new`, чтобы старый sidecar не мог неожиданно восстановиться после замены.
- При создании резервной копии сначала разрешаются recoverable `.bak`-состояния заметок и метаданных, чтобы не пропустить доступную предыдущую версию.
- Успешная транзакция фиксируется удалением маркера; очистка временной папки после commit остаётся best-effort и уже не затрагивает зафиксированные пользовательские данные.

### 5. Скрытое хранилище и аварийное уничтожение

- Маркеры начала и завершения очистки используют проверяемую атомарную запись.
- При восстановлении незавершённой очистки проверяется содержимое маркера.
- Удаляются базовые файлы и sidecar `.bak`/`.new`.
- Удаление скрытых данных теперь проверяется; очистка не заявляет успех, если файлы или каталоги остались.
- Перезапись выполняется без предварительного усечения существующего файла.
- Скрытая очистка по-прежнему не затрагивает основное хранилище.
- Аварийное уничтожение учитывает sidecar-файлы ключевого материала и сохраняет marker до последнего шага.

## Проверки

### Выполнено локально

Проведён отдельный Kotlin regression harness с API-shaped заглушкой Android `AtomicFile`. Он проверил:

- запись/чтение и повторную атомарную запись;
- имитацию неудачной фиксации новой версии — прежняя версия сохранилась, ошибка не была принята за успех;
- неудачную первую запись — незавершённый `.new` не считается сохранённым и удаляется;
- восстановление legacy `.bak`;
- удаление файла;
- создание и проверку verifier-записей скрытого и аварийного паролей;
- очистку скрытого хранилища с сохранением основных заметок, файлов и ключа;
- повторное создание скрытого хранилища после остатка незавершённой первой записи `.new`.

Результат harness: `PASS`.

Также выполнена проверка синтаксиса Kotlin-компилятором без Android SDK и AndroidX-зависимостей: диагностик парсера Kotlin (например, `expecting`, `unexpected tokens`, `redeclaration`) не обнаружено.

Отдельно локально выполнен блок статических проверок файлов/идентичности из текущего GitHub Actions workflow версии 1.4.14. Все его `test`/`grep`-проверки для исходников прошли. Это проверяет ожидаемую структуру и контрольные признаки проекта, но не заменяет Gradle build и unit-тесты.

### Не выполнено / требует CI или устройства

Полная команда Android Gradle:

```bash
gradle clean testDebugUnitTest assembleDebug --no-daemon --stacktrace
```

не запускалась: в доступной среде отсутствует Gradle, Gradle Wrapper и Android SDK. Попытка компиляции всех исходников обычным `kotlinc` не является полноценной сборкой и ожидаемо завершилась на отсутствующих Android/AndroidX/Compose зависимостях.

Не выполнялись реальные fault-injection испытания на Android-устройстве, тесты нехватки дискового пространства, принудительного завершения процесса на каждом шаге восстановления и независимый внешний аудит.

**Статус этапа:** исправления исходников подготовлены; этап не считается окончательно подтверждённым до прохождения `testDebugUnitTest` и `assembleDebug` в GitHub Actions или эквивалентной Android-среде.

## Исправление сборки после проверки GitHub Actions

В журнале GitHub Actions обнаружена ошибка компиляции:
`FileVaultRepository.kt:535:49 Unresolved reference: O_DIRECTORY`.

Причина: используемый Android SDK не предоставляет `OsConstants.O_DIRECTORY` как доступное Kotlin-имя константы. В `syncVaultDirectory()` оставлен `Os.open()` с `OsConstants.O_RDONLY`; путь уже указывает на приватный каталог приложения. Дескриптор по-прежнему закрывается в `finally`, а `Os.fsync()` вызывается для синхронизации каталога.

Это исправление устраняет указанную ссылку на отсутствующий символ. Полную задачу Gradle `clean testDebugUnitTest assembleDebug` необходимо повторно выполнить в GitHub Actions; успешная Android-сборка этим локальным патчем не заявляется.
